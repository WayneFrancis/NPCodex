# NPCodex

NPCodex is a local-first RPG Dungeon Master assistant for managing campaign worlds, NPCs, relationships, interactions and persistent AI memory.

## Local development

The development database is PostgreSQL 17 with the pgvector extension (tested target: PostgreSQL 17.11 / pgvector 0.8.7). Run it in Docker Desktop. Keep the local `.env` file containing your PostgreSQL password out of Git; `.gitignore` excludes it.

The existing local `compose.yaml` can be used to start the container:

```powershell
docker compose up -d
docker compose ps
```

The Compose file was configured locally before this repository was initialised. It is not yet tracked here; do not replace your existing local configuration without checking it.

## Apply initial database migration

1. In DBeaver, connect to the `npcodex` database on `localhost:5432`.
2. Open `database/migrations/0001_initial_schema.sql` in DBeaver's SQL editor (or paste in its full contents).
3. Use **Execute SQL Script** so the entire transaction is executed, not just the statement at the cursor.
4. Verify:

```sql
SELECT version, applied_at FROM schema_migrations;

SELECT table_name
FROM information_schema.tables
WHERE table_schema = 'public' AND table_type = 'BASE TABLE'
ORDER BY table_name;

SELECT extname, extversion FROM pg_extension WHERE extname = 'vector';
```

Expected migration version: `0001_initial_schema`. There should be **13 application tables**, including `schema_migrations`. pgvector should be version `0.8.7`.

**Run each migration only once.** The initial migration uses `CREATE TABLE` (not `IF NOT EXISTS`); if it was already applied, do not run it again. Add a new numbered migration for future changes.

## Database layout

- `campaigns` — separate tabletop campaigns
- `locations` — hierarchical regions, towns, buildings, rooms
- `factions` — guilds, houses, organisations
- `characters` — NPCs and player characters
- `character_location_roles` — ownership, residence, employment, etc.
- `character_factions` — membership and roles
- `character_relationships` — directed attitudes (A's view of B may differ from B's view of A)
- `interactions` and `interaction_participants` — persistent event/conversation records
- `memories` — facts and experiences **known by a particular character**
- `knowledge_sources` and `knowledge_chunks` — campaign or shared reference documents, split into searchable passages
- `schema_migrations` — applied migration versions

### Embeddings

The `memories.embedding` and `knowledge_chunks.embedding` columns are `VECTOR(768)`, intended for the `nomic-embed-text` embedding model through Ollama. The `embedding_model` is recorded alongside each vector. Embeddings may initially be null while text is waiting for processing.

pgvector does exact nearest-neighbour search without any special vector index. Add HNSW later only when performance measurements show a need.

An illustrative NPC memory query, once embeddings exist:

```sql
-- @query_embedding is a vector(768) parameter generated by the same model.
SELECT memory_id, content, embedding <=> @query_embedding AS cosine_distance
FROM memories
WHERE campaign_id = @campaign_id
  AND owner_character_id = @npc_id
  AND embedding_model = @embedding_model
  AND embedding IS NOT NULL
ORDER BY embedding <=> @query_embedding
LIMIT 10;
```

PostgreSQL positional parameter syntax differs from this application-level illustrative query; parameter binding will be implemented in the C# data-access layer.

**Security/knowledge boundary:** The application must enforce campaign and NPC scoping, and guard DM-only information before putting retrieved content into prompts. The `is_secret` flag is *not* database-level row security. An NPC may know something that players should not.

### Data integrity notes

Foreign keys for campaign-specific data use `(campaign_id, entity_id)` pairs so an NPC in one campaign cannot accidentally reference a location or interaction in another. Records intentionally do not cascade-delete by default; deleting campaign history should be explicit. Nested location cycles involving multiple rows are not yet prevented and must be validated in application logic.

## Phase 3: Local Ollama embeddings and NPC memory retrieval

The AI layer is in `src/NPCodex.AI`. It uses Ollama's local `POST /api/embed` endpoint with `nomic-embed-text` and the PostgreSQL `VECTOR(768)` fields already created by migration `0001_initial_schema`. No new migration is needed.

The first implementation runs on demand, not as a background worker. It does not invoke Qwen chat or expose NPC content to an external AI service.

1. Ensure your Ollama container is running, with host port `11434` available. For example, view containers using `docker ps`. If your container is named `ollama`, install the model:

```powershell
docker exec ollama ollama pull nomic-embed-text
```

If your container has a different name, substitute that name. This model is distinct from your existing `qwen3:8b` chat model.

2. Pull, restore and build the new .NET projects:

```powershell
cd D:\\dev\\NPCodex
git pull --ff-only
dotnet restore NPCodex.slnx
dotnet build NPCodex.slnx
```

3. Find your Test Campaign ID and Mira's character ID:

```powershell
dotnet run --project src/NPCodex.DevTools -- check
dotnet run --project src/NPCodex.DevTools -- show-world 1
```

Replace `1` with the campaign ID displayed by `check`.

4. Convert existing NPC memories into vectors:

```powershell
dotnet run --project src/NPCodex.DevTools -- embed-memories 1
```

The command processes up to 50 memories at a time. Rerun it for further batches. It is safe to rerun: vectors using the current model are skipped. Existing text memories are not modified. Ollama is asked **not to truncate** overlong text, so a memory that exceeds the model's context length will fail visibly rather than lose information. We will add chunking later.

5. Search Mira's memories semantically:

```powershell
dotnet run --project src/NPCodex.DevTools -- search-memories 1 1 "Did someone ask me to hold a map?"
```

Replace the first `1` with the campaign ID and second `1` with **Mira's actual character ID** from `show-world`. Retrieval is restricted to the NPC and campaign. Cosine distance is shown (lower = more similar); small numbers of memories do not prove ranking quality yet.

6. In DBeaver, confirm the model and embedding are stored:

```sql
SELECT c.name, m.memory_id, m.embedding_model,
       vector_dims(m.embedding) AS dimensions,
       m.content
FROM memories m
JOIN characters c
  ON c.campaign_id = m.campaign_id AND c.character_id = m.owner_character_id
WHERE m.campaign_id = 1
ORDER BY m.memory_id;
```

### AI embedding details

- Uses `search_document: ` when embedding stored memories and `search_query: ` when embedding questions, as recommended for this model family.
- Uses the official `Pgvector` .NET package with the Npgsql type mapper.
- Rejects vectors of the wrong length, nonfinite values, or zero length.
- Does not mix vectors made with different model names during queries.
- Writes a vector only when the memory's stored text still matches what was embedded.
- `NPCODEX_OLLAMA_URL` can override the default `http://localhost:11434/` address.
- Uses the existing `.env` PostgreSQL password reader; no password prompt.
- `search-memories` is **DM-only** and can show `is_secret` memories. Implement explicit player-safe filters before using retrieved results in any player-facing AI response.

## Phase 4: Qwen3 NPC dialogue preview

The new `npc-chat` command combines PostgreSQL facts and non-secret pgvector memories with your local `qwen3:8b` model. No database migration is required.

### Try it

Make sure the existing Ollama container is running and both models are installed:

```powershell
docker ps
docker exec ollama ollama list
```

If the Qwen3 model is missing: `docker exec ollama ollama pull qwen3:8b`. Replace `ollama` with the actual container name as needed.

Update your checkout and build:

```powershell
cd D:\dev\NPCodex
git pull --ff-only
dotnet restore NPCodex.slnx
dotnet build NPCodex.slnx
```

Find the campaign and Mira's actual NPC ID:

```powershell
dotnet run --project src/NPCodex.DevTools -- check
dotnet run --project src/NPCodex.DevTools -- show-world 1
```

Replace the campaign ID in `show-world` if needed. Embed any newly added memories:

```powershell
dotnet run --project src/NPCodex.DevTools -- embed-memories 1
```

Ask Mira about the map:

```powershell
dotnet run --project src/NPCodex.DevTools -- npc-chat 1 1 "Hello Mira, do you still have that map you promised me?"
```

The first `1` is the campaign ID. **The second `1` is Mira's NPC ID**; use her actual character ID from `show-world`. The result prints the NPC reply and the retrieved memory IDs with cosine distances.

### Current behaviour and limits

- Confirms the requested NPC belongs to the requested campaign.
- Sends only name, occupation, location, and location roles to the chat model. Excludes `dm_notes`, biography, and location descriptions.
- Searches up to five memories for that NPC and campaign; those explicitly marked `is_secret` are filtered out.
- Uses `nomic-embed-text` to embed the player's question, then `qwen3:8b` to write the response.
- Requests `think: false`, `stream: false` on the local Ollama `POST /api/chat` endpoint.
- Doesn't modify records or automatically save conversation text. The result is a **DM-only preview**.

**Not yet player-safe:** Although secret-marked memories are excluded, free-text data and generated output may still contain spoilers, fabrication or undesired content. A DM must approve the reply before showing it to players. Retrieved memories are context candidates, not proof that the model actually used each one.

The chat model defaults to `qwen3:8b`, and can be overridden using the `NPCODEX_CHAT_MODEL` environment variable. The Ollama address still defaults to `http://localhost:11434/` and can be changed with `NPCODEX_OLLAMA_URL`. PostgreSQL credentials still come from your local `.env` file.

Next: add an explicit **accept-and-record interaction** operation, so approved dialogue and resulting NPC memories are saved, and new memories are then embedded.

## Phase 5: Windows Dungeon Master interface (WinForms)

The first graphical frontend is in `src/NPCodex.Desktop`. It targets **.NET 10 for Windows** and uses the existing PostgreSQL data and local Ollama models. There is **no new database migration**.

### Run

In PowerShell:

```powershell
cd D:\dev\NPCodex
git pull --ff-only
dotnet restore NPCodex.slnx
dotnet build NPCodex.slnx
dotnet run --project src/NPCodex.Desktop
```

The application reuses the root `.env` password and defaults to Ollama at `http://localhost:11434/`. Docker Desktop, PostgreSQL and Ollama must be running. In Visual Studio you can open `NPCodex.slnx` and set `NPCodex.Desktop` as the startup project.

### First UI workflow

1. Select **Test Campaign** and **Mira Vale** on the left. Optionally select **Rowan** as the participating player character.
2. Type a player's spoken line.
3. Click **Generate 3 replies**. NPCodex makes one semantic memory retrieval and three Qwen3 chat requests. The three suggestions are **Natural**, **Warm**, and **Guarded**. They are editable. The **Manual reply** box works without the AI.
4. Select and optionally edit a reply. Inspect the retrieved memory IDs and texts at the bottom.
5. If the NPC should remember this exchange, check **Also save a memory**, then write or edit the memory. **Draft from dialogue** pre-fills an editable note about what was *said*, not any unconfirmed player action. Set importance 1–5 and optionally flag it Secret.
6. Click **Approve and save interaction** and confirm. The app stores the exact player line and chosen reply in an interaction transcript. Only when requested does it create a separate NPC memory linked to the interaction.
7. The **Memories** tab lists the selected NPC's stored memories (including secret ones, visible to the DM), and can create, edit, or delete memories. Saving modified text invalidates its old vector and attempts to embed the new text immediately. If Ollama is unavailable, the **database save still succeeds**, and the memory remains pending for the existing `embed-memories` command.

### Current limitations

- **DM only**, not a player-facing or authenticated multi-user app. The UI shows secret memories in the DM-only editor. Model output requires human review.
- Saves approved dialogue as an interaction; it does not assume any player action occurred just because a candidate mentions it.
- The three suggestions are generated sequentially; on local hardware this may take a while. The app keeps controls disabled while waiting.
- Memory editing checks the previously loaded text to prevent overwriting a different edit, but this is not yet a full multi-user concurrency protocol.
- No full-session chat log UI, autosave, streaming generation, or AI-generated memory extraction. Those are later enhancements.
- The desktop project has been committed but has **not yet been compiled/tested on the user's Windows environment**.

### Try a two-turn conversation with Mira

1. Choose your **Test Campaign**, **Mira Vale**, and optionally **Rowan** as the player character. Each different NPC/player pairing has its own conversation.
2. Ask, "I've heard the northern ruins are haunted. What do you think?" Generate three replies. Choose and edit one, then **Approve and save interaction**. You may leave the long-term memory checkbox **unchecked**.
3. The approved player line and NPC reply appear in the **Approved conversation history** tab at the bottom of the Dialogue page. This is short-term context, *not* a permanent NPC `memories` record.

**DM approval rule:** Only responses you explicitly approve join session history. Generating three candidates, changing a draft, or leaving a conversation unsaved does not update either `conversation_turns` or `memories`. Only choosing the optional **Also save a memory** creates a long-term NPC memory and queues its embedding.

To inspect saved turns in DBeaver:

```sql
SELECT s.session_id, c.name AS npc, s.started_at, s.ended_at,
       t.turn_id, t.player_line, t.npc_reply, t.approved_at
FROM conversation_sessions s
JOIN characters c
  ON c.campaign_id = s.campaign_id AND c.character_id = s.npc_id
JOIN conversation_turns t
  ON t.campaign_id = s.campaign_id AND t.session_id = s.session_id
WHERE c.name = 'Mira Vale'
ORDER BY s.session_id, t.turn_id;
```

**Limits:** Only the newest open session for a given campaign/NPC/player-character combination resumes automatically; closed sessions remain in the database but cannot yet be browsed in the UI. Only eight latest approved exchanges are sent to Qwen to bound context size; the entire approved transcript remains stored. Previously saved `interactions` aren't converted to session turns. This is still a DM-only prototype with no player authentication, and generated output must be reviewed before use. Database migrations are manual for now. Build/runtime verification must be performed on Windows.

### Phase 7 follow-up: disposition not noticeably changing replies

The original personality implementation sent a numerical disposition in JSON with
only a weak prompt instruction. Small local chat models often treated that as
background flavour. The dialogue service now adds explicit **behavioural guidance**
for seven disposition ranges: deeply hostile, strongly unfriendly, wary, neutral,
cautiously friendly, friendly, and strongly loyal/warm. This affects how warmly
the NPC addresses the selected PC, trust, patience and willingness to help
without fabricating reasons for the relationship.

Pull and build; **no new migration** is needed for this fix:

```powershell
cd D:\dev\NPCodex
git pull --ff-only
dotnet build NPCodex.slnx
dotnet run --project src/NPCodex.Desktop
```

To test with Mira:

1. Select **Mira Vale** **and Rowan** in the left sidebar. Selecting only
   Mira leaves the target PC unspecified, so no directed disposition is applied.
2. Under **Personality & Relationships**, set Rowan's disposition to `-100`.
   Ensure **Private opinion — do not send to Qwen** is **unchecked** and click
   **Save NPC opinion of player**. If checked, the opinion is deliberately not
   included in the model prompt, regardless of its score.
3. On the **Dialogue** tab, ask the same question as before and click
   **Generate 3 replies**. Read the new line immediately below the button; it
   should say something like `Applied Mira Vale → Rowan: -100 (deeply hostile).`.
   If it says *No player character selected*, *No saved attitude* or
   *PRIVATE — not sent to Qwen*, the relationship cannot affect the replies.
4. Change the score to `+35`, save again, and regenerate with the **same**
   question. The diagnostic line should now read
   `Applied Mira Vale → Rowan: +35 (cautiously friendly).`.
5. Compare the replies. A deeply hostile NPC should be distinctly colder and
   less inclined to assist than a cautiously friendly one, while honouring
   previously established campaign facts.

If testing in a previously established conversation, bear in mind that Qwen
receives the last eight approved dialogue turns. To isolate the disposition
effect, **End conversation / start new** before each test. Do not approve any
test replies unless they are intended to be part of the campaign.

To check the saved setting directly in DBeaver, replace the names if needed:

```sql
SELECT npc.name AS npc, pc.name AS player, r.disposition, r.is_secret,
       r.description
FROM character_relationships r
JOIN characters npc
  ON npc.campaign_id = r.campaign_id
 AND npc.character_id = r.source_character_id
JOIN characters pc
  ON pc.campaign_id = r.campaign_id
 AND pc.character_id = r.target_character_id
WHERE npc.name = 'Mira Vale'
  AND pc.name LIKE 'Rowan%'

```

NPCodex still provides **draft replies only**; DM approval is mandatory,
and local Qwen3 output is probabilistic, so behavioural instructions improve
consistency but cannot guarantee exact phrasing.


### Phase 7 follow-up: speak directly to the selected PC

An NPC memory is often written in third person (for example, "Rowan promised
to return with two gold pieces"). When **Rowan is the selected current player
character**, Mira must address Rowan directly: "You asked me to keep this map."

The dialogue service now resolves the selected PC's name **independently of
the relationship table** and provides it to Qwen as the current speaker. It
also instructs Qwen not to contradict stored facts or invent a broken promise
merely because a promise to pay exists. Disposition should alter the NPC's
tone, not rewrite known history.

### Phase 7 follow-up: speaker aliases and reply perspective verification

When the seeded player character is selected, NPCodex now recognises both
`Rowan (example PC)` (the database display name) and `Rowan`
(the name used by existing memories) as the **same current speaker**.
This mapping is specific to the seeded ` (example PC)` suffix; the app
does not automatically assume that arbitrary short names are unique aliases.

Generated candidate replies are checked for obvious third-person references
to the current speaker, such as `until Rowan returns`,
`Rowan promised`, or `Rowan's map`. Affected candidates receive one
additional local Ollama request to **revise wording only**, preserving tone,

### Chronology and older memories

The **Memories** tab displays `[Day N HH:mm]` for dated memories and
`[Undated]` for older ones. **Memory has a known in-world date/time** controls
whether manually edited memories acquire a game date; older undated memories
are not silently assigned Day 1 by merely opening the editor.

Semantic retrieval includes the memory's fictional day and time, and
excludes memories dated **after** the current fictional moment.
Qwen receives those dates and is instructed not to invent phrases like
"two weeks ago" when a memory is undated or when the day arithmetic does
not justify that elapsed time. Previously recorded interactions without an explicit
campaign day keep their unknown historical dates; earlier known campaign
days are reused without inventing a time of day. Fictional day numbers are system-neutral; support
for individual RPG calendars (e.g., named months) can be added on top of
the stored chronology.

Example audit:

```sql
SELECT i.interaction_id, i.world_day, i.world_time,
       i.summary, i.transcript
FROM interactions i
WHERE i.world_day IS NOT NULL
ORDER BY i.world_day DESC, i.world_time DESC, i.interaction_id DESC;

SELECT c.name AS remembered_by, m.memory_type,
       m.world_day, m.world_time, m.content
FROM memories m
JOIN characters c ON c.campaign_id = m.campaign_id
                 AND c.character_id = m.owner_character_id
WHERE m.memory_type = 'overheard'
ORDER BY m.memory_id DESC;
```

### History and searching

The history grid columns are:
1. Campaign date/time.
2. Speaking character.
3. Characters hearing that specific statement (excluding its own speaker).
4. What was said.

Click a header to sort. Right-click a header to enter a column-text filter.
The search box above the grid searches across **all approved statements in
the current campaign**, not just roster members. Each query creates a new
result tab with the same columns plus a **Relevance** score derived from

not paraphrased embeddings. It may miss conceptual matches without shared
words (for example, `having a sword made` versus `commissioning a blade`);
semantic search over statements could be added later.

### Who actually heard a statement?

On approving a dialogue exchange, both speakers are recorded as participants.
Normally all roster members can hear both spoken lines. The new
`conversation_statements` and `statement_hearers` rows capture who spoke
and exactly who heard **each utterance**, including the in-game clock.

speakers hear those statements; other roster members cannot receive
witness memories for that exchange. After a normal exchange, witnesses are
listed as hearers even if the DM disables automatic memory creation. With
**Give checked characters their own memory** enabled, the selected
characters also get dated first-person memories of what they heard.

The optional responding NPC memory is separate and remains DM-edited.
NPC and PC responders can both be recorded as the answerer, but automated
suggestions and optional reply-NPC memories only apply to NPC responders.
Saved dialogue is canonical *speech*, not automatically canonical truth.

Existing records are backfilled as fairly as the original participant data
allows; older exchanges did not have per-statement private-audience flags.
This edition does not yet model characters walking in/out mid-exchange,
eavesdropping checks, or selective hiding of a single line within one
approved two-line exchange. The private toggle applies to the current
exchange only.

location-alias and location-history support can explicitly represent former
names without altering what characters actually said.

  **Delete** unchecks the highlighted character; **Clear selection (all)**
  removes the restrictions.
- **Text / keywords** searches both PostgreSQL full-text terms and
  literal substrings. An empty search expression lists recent memories
  for the chosen owner(s), or the entire campaign.
- **Meaning (vectors)** uses `nomic-embed-text` through the existing
  local Ollama embedding client and compares to existing memory vectors
  with pgvector cosine distance. It can retrieve semantically similar
  memories that do not share the query's exact words. Enter a query;
  the semantic mode cannot meaningfully list results without one.
- The grid shows memory ID, owner, type, fictional day/time,
  DM-secret status, whether an embedding exists, the relevance score,
  and a text excerpt. Selecting a row shows the full text and owner in
  a read-only preview; PC memories are searchable even though the
  earlier Memories editing tab only edits NPC memories.
- **Include DM-secret memories** is checked by default because this
  is a DM-only application. Untick it to exclude secret memories.
  Searching does not send memory text to a third-party service: the
  query is embedded by local Ollama, then the private vector comparison
  takes place inside local PostgreSQL.
- Semantic search **only includes memories with current
  `nomic-embed-text` embeddings**. Use **Embed missing (up to 100)**
  to process a batch of unembedded memories for this campaign (both
  PC and NPC), then repeat for larger campaigns. It uses local Ollama
  and never modifies the actual memory text.
- Relevance scores from word matching and from vector cosine similarity
  are two different metrics and **are not directly comparable**. Both
  query modes are limited to a bounded result set (currently up to 300
  for text and 100 for vectors).

### What the legacy Windows recognizer can hear

The speech diagnostics already reported an installed `en-GB`
recognizer, `MS-2057-80-DESK`. Having a recognizer installed does not
prove that its in-process microphone capture or `DictationGrammar`
works in a particular Windows 11 configuration. Windows+H is a separate
voice-typing system and can work even when the older engine does not.

The recognition session now tracks input audio-level updates (including
peak microphone level, from 0 to 100), detected speech, hypotheses,
accepted phrases and rejected phrases. After you start and stop one
dictation session, right-click the text field and choose **Speech
recognizer diagnostics...** to see the last session counters.

Suggested test:
1. On Dialogue, right-click an editable field and choose Start dictation.
2. Speak a short, ordinary sentence (avoid fantasy names for this test).
   Look for microphone level changes or **Speech detected** at the bottom.
3. Stop dictation. Open diagnostics again. Record the
   **Audio updates, peak level, speech detected, hypotheses, recognized,
   rejected** counters.

If **Audio updates = 0** or peak stays zero, investigate the
`System.Speech` capture device/microphone stream, even if Windows+H works.
If the level changes but no words are recognized, focus on the installed
legacy recognition engine and its grammar. The intended eventual
upgrade is a modern local speech recognizer, for example a
Whisper-compatible engine, using the same context-menu workflow.

The changes are committed and reviewed statically; confirm the
Windows build and microphone behaviour locally.


## Phase 11 — Beliefs, rumours and DM-controlled prepared stories

**Apply this new migration once** in DBeaver, after
`0006_conversation_browser.sql`:

`database/migrations/0007_memory_provenance.sql`

It adds `memories.knowledge_status` (with a validated set of values) and
`memories.knowledge_source` (optional source attribution). Existing
memories are retained **unaltered**, with `knowledge_status='recollection'`
as the conservative default. Existing pgvector embeddings remain valid,
because the words of the memory have not changed.

### What the DM can now record

In the **Memories** tab, choose a memory and edit its **What kind of
knowledge?** dropdown and optional **Source** text. Then use the
regular Save memory button.

- **Recollection**: Something this particular NPC remembers; their
  recollection may be imperfect. Default for old and new memories.
- **Verified fact**: A DM-confirmed true fact this specific NPC knows.
  It is **not** automatically known to other characters.
- **Belief**: A subjective belief this character holds, possibly wrong.
- **Rumour**: Something heard from someone else; enter the source if
  known, such as `A sailor in the Dock Ward`.
- **Prepared lie**: A specific false statement deliberately created
  by the DM for this NPC to tell; the system must not invent supporting
  false events. It is **excluded** from generated dialogue by default.

These labels and source descriptions are stored per memory. The **Memory
Search** tab displays the knowledge label in its own column and shows the
source in the selected result's read-only preview.

### Effect on dialogue generation

Retrieved memories now carry their knowledge label/source into the
local Qwen prompt. The instructions distinguish DM-confirmed facts from
potentially mistaken beliefs and secondhand rumours. Characters may
speak their beliefs naturally while not treating them as global
objectively established facts. Prior approved speech continues to
be historical speech; it does not prove every spoken claim is true.

The Dialogue tab has **Permit DM-authored prepared lies in generated
replies**. It is **unchecked** by default. When checked, relevant
`cover_story` memories may be supplied to the model and it *may*
repeat an explicitly authored false claim when the relationship and
conversation justify it. The model is still instructed never to invent
new falsehoods or corroborating incidents. Permission resets when a
conversation is completed or a new campaign is chosen. A DM must
still inspect and approve every draft.

Secret-marked memories retain their prior safety behaviour and are
**never sent into normal reply generation**, regardless of the
prepared-lies checkbox. Memories must also be embedded with
`nomic-embed-text` to appear in the existing semantic retrieval. To
make an older or newly edited memory available, use the existing
embedding workflow.

For now, a **Verified fact** is a DM label on a character-specific
memory, not a separate campaign-wide authoritative fact registry.
Authoritative world events and propagation of corrected knowledge
to other NPCs are possible later phases.
